# .context.md — Security feature backend

## owner

@samyak (PM) · agent (initial build)

## purpose

Backend pipeline for the Takeoff v2 Security feature. Three jobs:

- `index.js` — orchestrator + detector registry. Runs every registered
  detector against an analyzer-output snapshot, collects findings,
  computes a stable per-finding fingerprint.
- `persist.js` — translates normalized findings into v2 Gap rows on
  the existing `suggestions` table. Dedupes by fingerprint, upgrades
  overlapping non-security gaps to security, otherwise inserts a new
  security-tagged gap.
- `score.js` — computes the 0–100 security score from the unaddressed
  security gaps, parallel to but independent from the readiness score.

The actual detector files live under `detectors/` and self-register by
appending to `TIER1` / `TIER2` in `index.js`. Slice (a) ships zero
detectors — the framework, schema, score, and endpoint only — so the
project always has a security score (100/100 by default) even before
any detectors land.

## constraints

- Security is a TAG on a v2 Gap, never a fourth category. The Gap row
  keeps its existing `v2_category` (`broken` / `missing_functionality`
  / `missing_infrastructure`) and adds `is_security = TRUE` plus a
  severity. Don't introduce a fourth category. Don't gate Gap shape
  changes on this module.
- Detectors MUST NOT log, persist, or transmit raw secret values. File
  path + line number + redacted snippet only. The existing
  `services/suggestion-rules.js#ruleEnvInCode` already follows this
  pattern — copy it for any detector that touches credentials.
- Detectors MUST NOT throw out of `run()`. If the orchestrator catches
  an exception, the detector counts as zero findings — better than
  taking down the entire takeoff pipeline because of a regex compile
  error in one rule.
- Detector findings carry a `file` field. Findings without one are
  dropped silently in `normalizeFindings` because we have no way to
  fingerprint them and the UI has nowhere to render them.
- Fingerprints (`computeFingerprint`) are SHA-256 of
  `detector::file::line` truncated to 32 hex chars. Two detectors
  flagging the same line for different reasons get separate rows;
  re-analysis of unchanged code yields the same fingerprint and
  therefore the same row (no duplicate). Don't extend the fingerprint
  with project id — we scope by `project_id` at the SQL layer.
- The DB CHECK constraint
  `suggestions_security_severity_consistency` enforces
  `is_security ↔ security_severity`. Code paths that flip either MUST
  set both. `lib/db.js#applySecurityFlags` and the persistence layer
  already do this; any new helper must too.
- Scores are independent. Don't multiply, weight, or otherwise mix the
  security score into the readiness score. The product header shows
  both side-by-side; they answer different questions.

## decisions

### Security as a tag, not a category
Discussed in the security-feature instructions doc and accepted up
front: a fourth category would force every gap to pick a single
identity (is this gap broken, or is it security?), which is wrong —
SQL injection is broken AND security; missing rate-limiting is
missing_infrastructure AND security. Tag-based modeling lets the
existing categorization rules keep working unchanged and lets the
security UI compose with the existing filter chips.
agent · 2026-05-06

### Score weights are aggressive at the top
Critical = -15 means a single critical drops the project below 90
(the readiness green/yellow boundary). That's the correct signal for
"do not deploy." Tuning these is a UX decision; keep them in
`score.js` so call sites never have to know.
agent · 2026-05-06

### Upgrade-before-insert beats insert-and-dedupe-later
When a new security finding overlaps an existing non-security gap on
file path, we tag the existing row instead of producing a sibling.
Two reasons: (1) the user has already triaged the existing row; we
shouldn't reset that work, and (2) the gap card is a better UX when
one row says "this is broken AND a security risk" than when two
sibling rows compete for attention. The overlap heuristic is
file-path containment — same primitive `routes/v2/gaps.js` already
uses for synthetic-gap dedupe.
agent · 2026-05-06 · see `services/security/persist.js#applySecurityFindings`

### Fail-soft orchestrator
A bad detector returns zero findings, not a thrown pipeline. Same
contract as `services/suggestion-rules.js#runStaticSuggestions`. The
takeoff pipeline already has a long enough critical path; one regex
typo shouldn't fail an entire analysis run.
agent · 2026-05-06

### Stable id derived from fingerprint
Each security gap row's `id` is `sha256(project_id:sec:fingerprint)`
truncated to 16 chars. Stable across re-analyses → a finding the user
rejected stays rejected on re-analysis instead of reappearing under a
fresh id. The `sec:` prefix in the hash input prevents collision with
the AI-suggestion ids produced by `services/suggestion-rules.js#makeId`.
agent · 2026-05-06
